# 支付方式与收款方式

简体中文 · [English](../en-US/PAYMENT_METHODS.md)

## 模型

GMPay Edge 使用以下五个层级：

1. **网络/平台（Rail）**：链上网络、交易所或数字钱包。
2. **资产（Asset）**：带精度和链上标识的币种。
3. **支付接入（Payment Access）**：HTTPS RPC、WSS、平台 API 或服务商入站 Webhook。
4. **支付方式（Payment Method）**：系统内置支持的网络/平台与资产组合。
5. **收款方式（Receiving Method）**：运营者真正提供给收银台的收款目标、只读账户凭证、币种范围和限额。

支付方式表示系统能力，不设置启停状态。是否对外可用由启用且通过验证的收款方式决定。链上 RPC API Key 属于接入配置，并保存在独立的加密凭据表中；交易所 UID、API Key、Secret、Passphrase 与 OKPay Shop ID 属于具体收款方式，公共平台连接只保存 API 地址和优先级。交易所与数字钱包的内置公共连接在全新数据库中默认启用且不可停用；修改 API 地址仍会保持启用。它们不控制收银台曝光，也不具有链节点健康状态。

平台 API 地址属于交易所/钱包连接配置。账户标识与只读凭证属于各收款方式并一起加密保存；修改它们后，该收款方式保持停用，直到目标与平台身份再次通过验证。区块链端点与 RPC API Key 只能配置在链上连接配置上。

所需确认数属于支付方式；平台账户类适配器通常使用 `1`。切勿使用带提现权限的交易所 Key，GMPay Edge 只需要账户身份和入账历史读取权限。

所有法币金额使用最小货币单位整数，资产金额使用带精度的资产单位整数字符串；时间长度内部统一为毫秒。禁止 JavaScript 浮点金额运算。

收款方式的订单最小值与最大值统一使用固定币种 USD，并以 USD 最小货币单位整数字符串保存在收款方式主表；同一收款方式绑定的所有资产共用该限额。其他法币订单在收银台曝光和分配收款目标前，先使用当前持久化汇率折算为 USD；服务商或链本身的转账下限仍由适配器校验。

## 默认目录与工作流

首次安装会初始化全部已实现网络/平台、内置资产目录、支付方式、连接模板、常用本地汇率记录与同步设置，但不会虚构收款地址或平台账户，收款方式由运营者显式创建。

1. 核对预置资产与 Token 合约。
2. 核对对应接入配置及其 RPC 或平台 API 地址。
3. 创建收款方式；链上填写地址，交易所/钱包填写账户标识与只读凭证。
4. 按需测试并启用链上接入配置。交易所与数字钱包的公共连接始终启用；平台测试使用收款方式中的加密凭证，不在连接表中展示。
5. 启用收款方式。目标与平台身份未通过验证，或没有已启用且健康检查通过的接入配置时，服务端拒绝启用。
6. 检查公共状态页与资产页，创建低价值订单，验证检测与 Webhook 投递。

每个收款方式只有一个启用开关。停用最后一个可用收款方式会立即把对应资产/网络从公共支付目录移除，但不会删除系统支付方式；重新启用会通过当前适配器重新校验已保存目标。活动订单持有不可变支付快照，修改或停用收款方式不能改写历史支付明细。

## 扫描完整性与供应商限制

生产扫描器不假设一次供应商响应包含全部付款。TRON 跟随 TronGrid `meta.fingerprint` 游标，TON Center v3 使用 `limit`/`offset`，Aptos Indexer 使用 GraphQL offset，Solana 跟随 `getSignaturesForAddress.before`，OKX Funding Bills 跟随官方 `after=billId` 游标。Binance Pay 没有分页游标，因此返回满 100 行时会按时间窗口确定性二分，直到每个子窗口完整。EVM ERC-20 Log 区间拆分为连续且供应商安全的区块窗口。每次历史遍历都以订单创建时间减 15 分钟时钟偏差为下界（TronGrid `min_timestamp`、TON Center `start_utime`/`start_lt`、Aptos `transaction_timestamp`、Solana `blockTime`、Binance/OKX 起始时间），共用地址的终身历史不会进入单次扫描。每个分页适配器都有有界的行数与页数守卫；触达上限时适配器返回最新行并标记为截断扫描，而不是失败，重复的供应商游标仍会显式失败。

定时派发器按 `last_payment_scan_at` 排序活动付款，并且只在 Cloudflare Queues 接受完整批次后才推进该值，因此活动订单多于配置批次时也能公平轮转，入队失败时重试同一批订单。每个订单还在一次完整成功扫描后保存单调递增的供应商游标。空扫描或失败扫描不推进游标；截断扫描只前进到适配器完整覆盖的区块（EVM），或在未扫描部分比返回行更旧时不前进（TRON、TON、Aptos、Solana）。落后于 Log 回看或原生区块窗口的 EVM 游标从窗口边缘恢复并推进到已扫描链头。无法唯一归属到共用地址订单的转账写入审计日志 `payment.scan_unattributed`（每笔转账每天一条），并把游标上限设为该区块以便后续重新发现。已检测的未确认交易在每次扫描（包括地址发现失败的扫描）都按哈希刷新，确认与重组检测不会被供应商故障阻塞。只有 `network`、`authentication`、`rate_limit`、`invalid_response` 故障会改变连接健康状态；单订单扫描上限与逻辑错误只记录 `payment.scan_failed`，不影响连接。

每个最久未扫描批次内先将 USDT 订单入队；同优先级保留原顺序。优先级不改变批次成员，因此其他资产仍能公平轮转；Queue 不保证实际投递和完成顺序。每次扫描只使用该订单不可变快照中的资产和目标，适配器缓存按收款方式、资产、目标隔离。USDT 扫描为空不会阻止 ETH 付款检测，反之亦然。

已支付和多付订单在配置的 `payments.reorg_monitor_ms` 窗口内（默认 86,400,000 毫秒即 24 小时）继续留在扫描轮转中，期间刷新已确认的交易事件。第一次供应商缺失只把链事件标记为 `missing`，不改变订单，恢复时静默；连续第二次缺失才记录重组并原子地把该付款从订单聚合中移除。

### Provider I/O 与重试预算

每次适配器操作共用一个 deadline：默认 8,000 ms，最大 30,000 ms。分页、校时、时间戳
重试、交易补充查询和直接查询阶段都不能重置 deadline。单个支付方式每次扫描最多选择
8 个已启用连接，按健康状态、优先级和 ID 排序后串行故障转移，不做投机竞速。每个供应商
响应正文在解析前限制为 8 MiB；更大或恶意的响应会使该操作失败，而不会被完整缓冲。

默认的单次适配器物理请求硬上限如下：

| 适配器 | 默认物理请求上限 | 内部重试/并发 |
| --- | ---: | --- |
| TRON 扫描 | 2,051 | 50 页、1,000 行，每笔交易读取一次 Transfer 事件，区块/事件补充请求最多并发 3 |
| EVM Token/原生扫描 | 1,004 / 1,121 | Log 回看 3,000 区块、原生转账窗口 120 区块、最多 1,000 个匹配事件，区间串行 |
| EVM 直接查询 | 4 | 前三项并行读取和一次区块读取共用 deadline |
| TON / Aptos 扫描 | 50 | 分页串行，不在适配器内重试 |
| Solana Token/原生扫描 | 1,801 / 1,050 | 最多 16 个 Token Account、1,000 个签名，RPC 串行 |
| Binance Pay 历史 | 102 | 100 个拆分窗口，最多一次校时和一次时间戳重试 |
| OKX 入金扫描/直接查询 | 52 / 1,602 | 50 页；直接查询最多 32 个资产；全程最多一次校时重试 |
| OKPay 创建/查询 | 1 | 不在适配器内重试 |

这些数字是硬上限而不是正常请求量；慢请求通常会先被共享 deadline 终止。Payment Queue
最多同时运行 2 个消费者实例，每个实例最多并发处理 2 个支付消息，因此最多 4 个订单
同时执行 Provider 操作。在此边界内，TRON 区块补充请求最多并发 12，EVM HTTP/WSS
操作最多同时 8 个；其余适配器在单订单内串行。一个支付消息只有首次投递和最多 5 次
平台重试，之后进入 DLQ。适配器不自行重试普通瞬时错误；Binance/OKX 只允许在时间戳
错误时于同一 deadline 内重放一次签名请求，避免适配器、故障转移和 Queue 重试形成无界乘法。

## Alchemy 入站通知

Alchemy Address Activity 可降低 Ethereum、Base、BNB Smart Chain 与 Polygon
的发现延迟。它只是可选触发器，不是入账权威：GMPay Edge 先把验签后的通知持久化到
D1，Queue 中只发送内部事件 ID，再通过已配置的 EVM RPC 适配器重新获取交易。网络、
合约、目标地址、Event Index、金额、确认数、执行结果与规范区块状态均以这次权威查询
为准，随后才进入原有的原子支付处理器。Alchemy、Queue 或 RPC 索引延迟时，定时支付
扫描仍是恢复路径。

每个网络配置一个专用 Alchemy Webhook：

1. 打开“后台 → 支付设置 → 支付接入”，点击“新建推送”。表单会在保存前生成
   最终回调 URL，先复制该地址。
2. 在 Alchemy 为对应网络创建专用 Address Activity Webhook，并使用该 URL。不要与其他
   应用共用：地址对账把 GMPay Edge 视为唯一所有者，会移除不属于已启用收款目标或保留
   订单锁的远端地址。
3. 填写 Alchemy 的 Webhook ID、Signing Key 与 Auth Token。GMPay Edge 根据所选内部网络
   自动确定官方主网标识；密钥加密保存，列表 API 永不回传。
4. 保持默认“影子”模式，启用接入并执行“对账地址”；只有远端 Webhook 存在，且类型、网络、
   回调 URL、启用状态和托管地址都与本地来源一致时才会标记为健康。
5. 用低价值资金演练重复、延迟、少付、多付和重组。影子事件会完整执行入站验签与 RPC
   复查，但不修改资金状态；与常规定时扫描结果核对后再切换为“启用入账”。

入站签名按原始请求正文逐字节计算。轮换 Signing Key 时系统自动保留旧 Key 作为上一把
验签密钥，确认 Alchemy 完成切换后再明确清除。Auth Token 只用于有界的地址管理 API。
通过验签的投递还会按事件源在权威 D1 中限制为每分钟 600 次、原始请求最大 2 MiB、每次
最多 2,000 个 Activity；单个来源最多管理 2,000 个地址。远端地址列表超过有界分页读取
范围时，对账会用权威本地完整列表替换远端列表。停用来源会安排清除其托管地址；停用
期间，已正确签名的端点请求返回成功但不接收事件。通过验签的 Alchemy 供应商错误通知
会被确认接收但不会创建支付事件，同时将来源降级以供运营人员检查。

供应商事件以“来源 + 供应商事件 ID + Activity Index”幂等。事件一旦提交到 D1，即使
Worker 已返回或 Queue 暂时失败也不会丢失；定时维护会恢复到期事件与过期处理租约。
多个订单共用收款地址时，只接受已存在的交易归属或唯一匹配剩余金额；无法唯一判断的
转账保留为歧义事件，不猜测入账。“后台 → Webhook → 入站记录 → 支付事件”会展示复查状态、
尝试次数和已脱敏的错误码。具有 `webhooks:update` 权限的运营人员只能手动重新入队失败、
终止、歧义或明确可恢复的忽略事件；成功及处理中的事件不能从界面重放。

## 本地汇率

订单报价以 D1 汇率行为准。USD、USDT、USDC 使用内置 1:1 平价，不保存冗余快照行。加密资产汇率保存“资产/USDT”观测，法币汇率保存“USD/法币”观测。

报价优先使用订单币种与支付资产的直接观测；USD、USDT、USDC 在任一侧可互换，因此 `USD` 订单可直接用 `ETH/USDT` 报价 `ETH`。其他法币经 USD 桥接：应付资产数量为 `金额 ÷ USD/法币 ÷ 资产/USDT`，以精确整数运算一次计算并向上取整。订单快照记录两段汇率的乘积作为原始与最终汇率、基点调整之和、较早的观测时间，以及用 `+` 连接的两个来源。已同步的汇率仅在 `expires_at` 之前可用于报价，过期后报价返回汇率不可用，直到下一次同步成功或手动更新；`observed_at = 0` 的内置默认汇率在首次同步替换前仍可报价。

每个汇率页面都有自己的同步设置。加密汇率选择 Binance 或 OKX 与自动同步周期；法币汇率选择服务商（当前为 `exchangerate.host`）、其 API Key、自动同步周期和基点调整。每类都有独立的自动同步开关。每分钟 Cron 跳过已关闭的类别，并仅在保存的周期到期时执行；“立即执行”会先保存当前设置，再忽略自动同步开关和到期检查执行一次。

全新数据库只初始化可同步的币对，不用 `0` 伪造行情。首次成功观测前，`raw_rate` 与 `rate` 为空，后台列表显示 `—`，订单报价忽略该行。

每条已同步记录同时保存供应商 `raw_rate` 与最终 `rate`；同步以精确十进制运算应用配置的基点调整后再写入最终值。两个列表都显示“原始汇率”与“汇率”，没有来源或基点列。手动编辑任一类别只修改最终 `rate`，保留上一次供应商原始值、来源和观测时间，下一次成功同步再次更新两者。加密汇率每次只请求一次供应商批量行情，再以一个 D1 批次写入；缺失币对不会覆盖旧值，并记录安全失败摘要。系统没有独立的汇率策略表或同步来源表。

## 汇率同步

Binance Spot 与 OKX Spot 观测使用有界并发，一个缓慢的 ticker 不会串行化全部币对。每个加密币对相互隔离：失败或畸形的供应商响应永不覆盖其上一次观测。法币同步规范化服务商的 USD 报价表，插入或更新合法的三字母币种行，同时保留原始值与调整后的值。

每次刷新返回已配置、已更新和失败的数量。部分失败写入一条结构化审计摘要，只包含来源、币对和稳定错误码，不持久化服务商响应正文。成功的定时运行不会产生每分钟的审计噪音，管理员触发的运行始终归属到其操作者、Request ID 与来源 IP。

## 链上网络

链上连接配置（“RPC 节点”）共用同一套管理模型。新建 RPC 节点默认停用；启用前请先在行操作中测试节点，启用本身会再次执行实时健康检查，失败则拒绝。已启用节点由定时维护再次检查，RPC 表中显示当前延迟与健康/不健康状态。

内置 HTTPS 模板在安装时启用，以便定时健康检查立即评估；只有检查报告健康且有已启用、已校验的收款方式选中对应支付方式时，才会对订单可用。内置 WSS 模板保持停用，优先级为 200。默认数据对账只补缺失的目录默认项并保留运营者编辑的记录。

RPC 节点可以在不删除引用的情况下编辑。API Key 留空保留已存储值，明确的清除开关才会删除它。修改网络、端点 URL 或 API Key 会使之前的健康结果失效、原子停用节点，并要求重新测试成功后才能启用；仅修改名称或优先级保留当前启用与健康状态。审计元数据记录凭据是否变更，但绝不记录其值。

### TRON、TRX 与 TRC20

- 适配器：`tron`
- 预置 RPC：`https://api.trongrid.io`
- 收款目标：以 `T` 开头的 Base58Check 地址
- 原生资产：TRX，6 位
- 预置代币：USDT TRC20，6 位

RPC 节点字段：

```json
{
  "url": "https://api.trongrid.io",
  "apiKey": "optional TronGrid API key"
}
```

适配器读取 TRX 交易与 TRC20 转账，校验目标、资产与金额，跟踪区块确认，拒绝失败交易，并识别规范区块变化。TRC20 只接受资产上预置的代币合约：TronGrid 历史查询携带 `contract_address`，每行 `token_info.address` 与每个 Transfer 事件的合约都与该地址比对，资产代码来自配置而非供应商 symbol，仅共享 `USDT` 符号的仿冒代币会被忽略。每笔 TRC20 转账以真实 Transfer 事件索引标识（每笔交易读取一次事件），同一交易内的两笔同代币转账保持独立，哈希刷新解析同一事件。确认数以固化区块头（`/walletsolidity/getnowblock`）计算；付款人提交的 TRC20 哈希还要求 `receipt.result = SUCCESS`。每笔观测到的转账都在其自身区块高度解析 `blockID`（每次扫描去重），而不是使用移动的链头哈希，因此确认数增长不会被误判为重组。API Key 属于 RPC 节点，不属于全局运行时设置。

### Ethereum、Base、BNB Smart Chain、Polygon

- 适配器：`evm`
- 收款目标：20 字节 `0x` 地址
- 支持的原生资产：预置的 ETH、BNB、MATIC
- 支持的代币：预置的 USDT/USDC 合约

每个网络配置一个 JSON-RPC 连接配置。运行时根据所选资产、预置合约/精度、网络代码和健康的已启用端点构造适配器。

```json
{
  "url": "https://your-network-rpc.example",
  "apiKey": "optional provider key"
}
```

共享的 EVM 适配器扫描原生转账与 ERC20/BEP20 `Transfer` Log。付款人提交的交易 Hash 按支付方式配置的 Token 合约、收款地址和可选 Log Index 解析，而不是信任回执中的第一条 `Transfer` 事件；原生付款忽略无关的代币 Log。生产前请向发行方核对每个代币合约与精度。内置 HTTPS 模板默认启用以便健康评估，但在健康且存在已启用、已校验的收款方式之前不会对订单可用。EVM 连接还支持安全的 `wss://` JSON-RPC。WSS 模板默认停用且优先级为 200；启用后，选中的 WSS 订阅与权威 HTTP 轮询并行运行。订阅被拒绝或断线会记录 WSS 健康状态但不丢弃 HTTP 结果，下一次有界 Queue 扫描会从已保存游标重新连接。推送的 Log 只有在重新获取的交易回执中包含配置合约的同一条 Log 时才被接受。WSS 端点不会收到 Bearer API Key 头，供应商密钥需按其文档嵌入 `wss://` URL。原生 ETH/BNB/MATIC 转账每个区块需要一次完整区块读取，因此轮询每次只覆盖最近 120 个区块并从已保存游标续扫；落后于该窗口的扫描会跳过缺口，窗口之外的原生付款依赖付款人提交哈希、Alchemy 通知或 WSS 恢复，而不是轮询。

## 地址锁与迟到付款

收款方式金额锁还带有复用隔离期。订单完成、取消或过期会释放其活动预留，但相同目标、资产与预期资产单位金额在原订单过期时间加配置的重组监控窗口之前不能再次分配，避免旧订单的迟到付款被归属到复用同一金额的新订单。修改监控窗口只影响新分配的订单，不会改写不可变订单快照与已有锁的截止时间。

付款已覆盖全额的订单（`confirming`）不会过期：它在达到所需确认数后完成，或在链重组后回到 `pending`。已归属到过期或取消订单的付款，其确认数更新不经过迟到付款策略：付款确认后订单直接完成，否则订单保持终态，仅同步付款记录与余额。待审核的迟到转账以 `pending_review` 保存，在管理员接受前不计入订单余额，拒绝也不改变余额。已确认付款的确认数继续增长只会刷新已保存的确认数，不会再次发出订单事件或改写 `paid_at`。

在订单版本竞争中失败的并发选择以 `order_conflict` 报告，不会被当作金额碰撞重试。

## 付款人主动复核

定时检测延迟时，付款人可以在收银台选择“已付款但未确认”并提交供应商交易标识。服务端不信任该声明：它用配置的适配器拉取交易，核对订单的收款目标、网络和资产，然后才把规范化事件送入正常的幂等入账路径。提交由 D1 限流器按订单和客户端地址限制为每分钟 5 次。

## 默认数据恢复

已有安装早于新增默认项时，可执行“后台 → 运维中心 → 重置支付默认数据”。该操作使用“缺失即插入”语义，补回缺失的网络/平台、资产、连接模板、支付方式、汇率和同步设置，不启用或覆盖运营者配置，可重复执行。

## 密钥与日志

交易所与钱包凭证随收款方式一起加密；平台 API 地址与链上 RPC API Key 属于连接配置，后者保存在独立的加密凭据表中。API 响应与审计日志永不暴露平台密钥、签名密钥或 Webhook Secret。任何适配器都不接受钱包私钥或助记词。

## 生产检查

- 向发行方核对网络、合约/Mint/Master/Type 与精度。
- 确认收款目标归部署运营者所有。
- 使用只读平台凭证与 IP 白名单。
- 完成适配器健康检查与低价值真实支付。
- 验证待支付、确认、已支付、少付、多付、过期、迟到与重组行为。
- 验证 Webhook 签名校验、重试和重复事件处理。
- 每次配置变更后复核审计日志。

## 真实平台验证

自动化质量门只使用脱敏 Fixture，不需要网络凭证、外部账户或真实资金。链、交易所、钱包和 Telegram 的 Smoke 套件保留为可人工检查的资产，但全部无条件跳过，环境变量不能启用它们。生产验证仍是运营者显式执行的验收工作，不作为自动化证据报告。
