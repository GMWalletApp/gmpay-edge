# 支付方式与收款方式

简体中文 · [English](../en-US/PAYMENT_METHODS.md)

## 模型

GMPay Edge 使用以下层级：

1. **网络/平台（Rail）**：链上网络、交易所或数字钱包。
2. **资产（Asset）**：带精度和链上标识的币种。
3. **支付接入（Payment Access）**：HTTPS RPC、WSS、平台 API 或服务商入站 Webhook。
4. **支付方式（Payment Method）**：系统支持的网络/平台与资产组合。
5. **收款方式（Receiving Method）**：运营者真正提供给收银台的收款目标、只读账户凭证、币种范围和限额。

支付方式表示系统能力，不设置启停状态。是否对外可用由启用且通过验证的收款方式决定。链上 RPC API Key 属于接入配置；交易所 UID、API Key、Secret、Passphrase 与 OKPay Shop ID 属于具体收款方式，公共平台连接只保存 API 地址和优先级。交易所与数字钱包的内置公共连接在全新数据库中默认启用且不可停用；修改 API 地址仍会保持启用。它们不控制收银台曝光，也不具有链节点健康状态。

所有法币金额使用最小货币单位整数，资产金额使用带精度的资产单位整数字符串；时间长度内部统一为毫秒。禁止 JavaScript 浮点金额运算。

收款方式的订单最小值与最大值统一使用固定币种 USD，并以 USD 最小货币单位整数字符串
保存在收款方式主表；同一收款方式绑定的所有资产共用该限额。其他法币订单在收银台曝光
和分配收款目标前，先使用当前持久化汇率折算为 USD；服务商或链本身的转账下限仍由适配器校验。

## 默认目录与工作流

首次安装会初始化全部已实现网络/平台、资产、支付方式、连接模板、常用汇率与同步设置，但不会虚构收款地址或平台账户。

1. 核对资产、Token 合约/Mint/Master/Type 与精度。
2. 核对接入配置中的 RPC 或平台 API 地址。
3. 创建收款方式；链上填写地址，交易所/钱包填写账户标识与只读凭证。
4. 测试并按需启用链上接入配置。交易所与数字钱包的公共连接始终启用，平台测试从收款方式读取加密凭证，不在公共连接表展示。
5. 启用收款方式。目标、平台身份和可用接入验证失败时服务端拒绝启用。
6. 检查公共状态/资产页，创建低价值订单，验证检测、确认与 Webhook。

停用最后一个可用收款方式会立即把对应资产/网络从公共目录移除，但不会删除系统支付方式。活动订单持有不可变支付快照，配置变化不能改写历史订单。

## Alchemy 入站通知

Alchemy Address Activity 可降低 Ethereum、Base、BNB Smart Chain 与 Polygon
的发现延迟。它只是可选触发器，不是入账权威：GMPay Edge 先把验签后的通知持久化到
D1，Queue 中只发送内部事件 ID，再通过已配置的 EVM RPC 适配器重新获取交易。网络、
合约、目标地址、Event Index、金额、确认数、执行结果与规范区块状态均以这次权威查询
为准，随后才进入原有的原子支付处理器。Alchemy、Queue 或 RPC 索引延迟时，定时支付
扫描仍是恢复路径。

每个网络配置一个专用 Alchemy Webhook：

1. 打开“后台 → 支付设置 → 支付接入”，点击“新建推送”。表单会在保存前生成
   最终回调 URL，先复制该地址。
2. 在 Alchemy 为对应网络创建专用 Address Activity Webhook，并使用该 URL。不要与其他
   应用共用：地址对账把 GMPay Edge 视为唯一所有者，会移除不属于已启用收款目标或保留
   订单锁的远端地址。
3. 填写 Alchemy 的 Webhook ID、Signing Key 与 Auth Token。GMPay Edge 根据所选内部网络
   自动确定官方主网标识；密钥加密保存，列表 API 永不回传。
4. 保持默认“影子”模式，启用接入并执行“对账地址”；只有远端 Webhook 存在，且类型、网络、
   回调 URL、启用状态和托管地址都与本地来源一致时才会标记为健康。
5. 用低价值资金演练重复、延迟、少付、多付和重组。影子事件会完整执行入站验签与 RPC
   复查，但不修改资金状态；与常规定时扫描结果核对后再切换为“启用入账”。

入站签名按原始请求正文逐字节计算。轮换 Signing Key 时系统自动保留旧 Key 作为上一把
验签密钥，确认 Alchemy 完成切换后再明确清除。Auth Token 只用于有界的地址管理 API。
通过验签的投递还会按事件源在权威 D1 中限制为每分钟 600 次、原始请求最大 2 MiB、每次
最多 2,000 个 Activity；单个来源最多管理 2,000 个地址。远端地址列表超过有界分页读取
范围时，对账会用权威本地完整列表替换远端列表。停用来源会安排清除其托管地址；停用
期间，已正确签名的端点请求返回成功但不接收事件。通过验签的 Alchemy 供应商错误通知
会被确认接收但不会创建支付事件，同时将来源降级以供运营人员检查。

供应商事件以“来源 + 供应商事件 ID + Activity Index”幂等。事件一旦提交到 D1，即使
Worker 已返回或 Queue 暂时失败也不会丢失；定时维护会恢复到期事件与过期处理租约。
多个订单共用收款地址时，只接受已存在的交易归属或唯一匹配剩余金额；无法唯一判断的
转账保留为歧义事件，不猜测入账。“后台 → Webhook → 入站记录 → 支付事件”会展示复查状态、
尝试次数和已脱敏的错误码。具有 `webhooks:update` 权限的运营人员只能手动重新入队失败、
终止、歧义或明确可恢复的忽略事件；成功及处理中的事件不能从界面重放。

## Provider I/O 与重试预算

每次适配器操作共用一个 deadline：默认 8,000 ms，最大 30,000 ms。分页、校时、时间戳
重试、交易补充查询和直接查询阶段都不能重置 deadline。单个支付方式每次扫描最多选择
8 个已启用连接，按健康状态、优先级和 ID 排序后串行故障转移，不做投机竞速。

默认的单次适配器物理请求硬上限如下：

| 适配器 | 默认物理请求上限 | 内部重试/并发 |
| --- | ---: | --- |
| TRON 扫描 | 1,051 | 50 页、1,000 行，区块补充请求最多并发 3 |
| EVM Token/原生扫描 | 1,004 / 4,001 | 回看 3,000 区块、最多 1,000 个匹配事件，区间串行 |
| EVM 直接查询 | 4 | 前三项并行读取和一次区块读取共用 deadline |
| TON / Aptos 扫描 | 50 | 分页串行，不在适配器内重试 |
| Solana Token/原生扫描 | 1,801 / 1,050 | 最多 16 个 Token Account、1,000 个签名，RPC 串行 |
| Binance Pay 历史 | 102 | 100 个拆分窗口，最多一次校时和一次时间戳重试 |
| OKX 入金扫描/直接查询 | 52 / 1,602 | 50 页；直接查询最多 32 个资产；全程最多一次校时重试 |
| OKPay 创建/查询 | 1 | 不在适配器内重试 |

这些数字是硬上限而不是正常请求量；慢请求通常会先被共享 deadline 终止。Payment Queue
最多同时运行 2 个消费者实例，每个实例最多并发处理 2 个支付消息，因此最多 4 个订单
同时执行 Provider 操作。在此边界内，TRON 区块补充请求最多并发 12，EVM HTTP/WSS
操作最多同时 8 个；其余适配器在单订单内串行。一个支付消息只有首次投递和最多 5 次
平台重试，之后进入 DLQ。适配器不自行重试普通瞬时错误；Binance/OKX 只允许在时间戳
错误时于同一 deadline 内重放一次签名请求，避免适配器、故障转移和 Queue 重试形成无界乘法。

## 汇率

订单报价以 D1 汇率为准。USD、USDT、USDC 使用内置 1:1，不保存冗余行。加密汇率保存“资产/USDT”，法币汇率保存“USD/法币”。

加密汇率可选择 Binance 或 OKX；法币汇率当前使用 `exchangerate.host` 并保存 API Key。全新数据库只初始化待同步币对，不用 `0` 伪造行情；首次同步前原始汇率和最终汇率为空，后台显示 `—`，订单报价不会使用未观测值。每类都可独立配置自动同步开关、同步周期和基点调整。每分钟 Cron 跳过已关闭的类别，并仅在保存的周期到期时执行；设置弹窗中的“立即执行”会先保存当前配置，再忽略自动同步开关和到期检查执行一次。加密汇率每次只请求一次供应商批量行情，再批量写入 D1；同步以精确十进制计算，把供应商 `raw_rate` 和调整后的 `rate` 一起写入。手动编辑只修改最终汇率，保留原始观测；下次同步再次更新两者。缺失币对不会覆盖旧值，并会记录安全失败摘要。

## 链上网络

### TRON

- 默认 RPC：`https://api.trongrid.io`
- 目标：以 `T` 开头的 Base58Check 地址
- TRX：6 位；TRC20 USDT：6 位
- 适配器校验目标、资产、金额、交易状态、区块确认与规范区块变化。

### Ethereum、Base、BNB Smart Chain、Polygon

- 复用 EVM JSON-RPC 适配器，支持原生转账与 ERC20/BEP20 `Transfer` Log。
- 目标为 20 字节 `0x` 地址。
- 付款人提交 Hash 时必须按配置 Token 合约、目标地址和可选 Log Index 精确匹配，不能取第一条无关 Transfer。
- 内置 HTTPS 模板安装后默认启用，以便定时健康检查立即验证；只有健康节点和已启用、已校验的收款方式同时存在时才会对订单可用。
- WSS 模板默认停用且优先级为 200。启用后，选中的 WSS 订阅与权威 HTTP 轮询并行；订阅被拒绝或断线会更新 WSS 健康状态，但不会丢弃 HTTP 扫描结果，下一次有界 Queue 扫描会从已保存游标重新连接。

### TON

- 默认 API：`https://toncenter.com/api/v3`
- 目标：`EQ…` 或 `UQ…` 用户友好地址
- 原生资产 9 位，另支持 Jetton USDT；生产前必须核对 Jetton Master。

### Aptos

- 默认 Indexer：`https://api.mainnet.aptoslabs.com/v1/graphql`
- 目标：最长 64 个十六进制字符的 `0x` 地址
- 支持 APT、USDT、USDC；使用稳定 `event_index` 做链事件幂等。

### Solana

- 默认 RPC：`https://api.mainnet-beta.solana.com`
- 目标：Base58 钱包地址
- 支持 SOL、SPL USDT、USDC；默认要求 finalized commitment。

## 交易所与数字钱包

### Binance

收款方式保存：

```json
{
  "receiverUid": "numeric Binance UID",
  "apiKey": "read-only API key",
  "secretKey": "API secret"
}
```

默认 API 为 `https://api-gcp.binance.com`。启用前会验证检测实际使用的签名 Pay History 权限。Binance 不通过无关的 Spot Account 接口提供收款 UID，因此系统校验已配置 UID 的数字格式，并且只接受 `receiverInfo.binanceId` 与收款方式 UID、资产同时匹配的历史记录。Key 只授予 Pay History 读取权限并建议设置 IP 白名单；适配器不会交易或提现。

### OKX

```json
{
  "accountUid": "numeric account UID",
  "apiKey": "read-only API key",
  "secretKey": "API secret",
  "passphrase": "API passphrase"
}
```

默认 API 为 `https://www.okx.com`。签名账户响应必须匹配 UID，只接受目标资产的正向 Funding Bill。地区账户应使用平台分配的地区域名。

### OKPay

```json
{
  "shopId": "shop identifier",
  "apiKey": "shop signing API key"
}
```

默认 API 为 `https://api.okaypay.me/shop`。系统创建托管支付 URL、保存供应商订单号、校验签名回调并轮询状态。公共回调为 `/api/providers/okpay/notify`；客户端传入的状态、金额、资产、Shop 身份和签名必须再次经适配器验证。

## 地址锁与迟到付款

收款方式按“目标 + 资产 + 预期资产单位金额”加锁。订单完成、取消或过期会释放活动锁，但相同组合在原订单过期时间加链重组监控窗口之前不能复用，避免旧订单迟到付款误归属新订单。

已支付和多付订单在 `payments.reorg_monitor_ms` 窗口内继续扫描。第一次供应商缺失只把链事件标记为 missing；连续第二次缺失才记录重组并原子回滚订单聚合。

## 付款人主动复核

收银台“已付款但未确认”允许提交供应商交易标识。服务端会用当前适配器拉取真实交易，核对收款目标、网络和资产，再进入正常幂等入账路径；不会信任用户声明。D1 原子限流器按订单和客户端限制提交频率。

## 默认数据恢复

需要恢复内置目录时可执行“后台 → 运维中心 → 重置支付默认数据”。操作只补缺失的网络、资产、连接模板、支付方式、汇率和同步设置，不启用或覆盖运营者配置，可重复执行。

## Smoke 测试

默认测试只使用脱敏 Fixture，不需要网络凭证、外部账户或真实资金。链、交易所、钱包和 Telegram 的真实平台 Smoke 保留为人工检查资产，但全部无条件跳过，不能通过环境变量启用。生产平台验证属于运维人员单独执行的验收工作，不能把 Fixture 测试当作真实平台证据。

## 生产检查

- 向发行方核对网络、合约/Mint/Master/Type 与精度。
- 确认收款目标归部署运营者所有。
- 交易所只使用只读凭证和 IP 白名单。
- 完成适配器健康检查与低价值真实支付。
- 验证待支付、确认、已支付、少付、多付、过期、迟到与重组行为。
- 验证 Webhook 签名、重试和重复事件处理。
- 每次配置变更后复核审计日志。
