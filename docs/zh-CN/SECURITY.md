# 安全说明

简体中文 · [English](../en-US/SECURITY.md)

## 账户与权限

- 禁止公开邮箱注册。新部署实例按产品设计公开 `/install`，供运营者原子创建首位受保护的
  `root` 用户；该用户提交后安装流程即关闭，后续账户只能由具有所需动态 RBAC 权限的登录用户
  在用户管理界面创建。直接请求 Better Auth 的邮箱注册端点会被拒绝，不会创建用户或凭据账户。
- Better Auth 管理密码和 Session。密码只校验长度，Hash 前不做 Trim 或其他规范化。root 用户
  初始化在并发请求下保持原子；普通用户/凭据创建以及改密与撤销 Session 也通过 D1 原子批次提交。
  禁用用户不能创建 Session，所有禁用路径都会撤销现有 Session，重新启用会清除禁用时间。
  删除用户后，历史审计操作者和设置编辑者置为 `NULL`，记录得以保留且没有悬空外键。
- 登录、找回密码请求与重置密码在所有实例共享的权威 D1 计数表中限流：登录每个客户端地址
  每分钟 5 次、每个账户每 15 分钟 30 次；找回请求每地址每分钟 3 次；重置完成每地址每分钟
  5 次。Better Auth 的内存限流只是每个实例尽力而为的第一层。Host、Origin、CSRF 与 Better Auth
  可信来源检查共用已校验的 `security.allowed_hosts` 列表；非本地主机视为 HTTPS 来源，
  localhost 回环条目在开发环境使用 HTTP。
- 用户最终权限是全部启用角色权限的并集。每条角色-模块记录保存一个经校验的
  `permission_mask`；模块与操作注册表由代码定义，未知模块或位值失败关闭。自定义角色可以
  在不删除绑定的情况下停用：服务端每次请求只联结启用角色，停用立即移除有效权限，重新启用
  恢复原有绑定。内置 `root` 角色不能修改、删除或停用。
- 编辑、禁用、重新启用或删除 root 用户必须由当前启用的 root 用户执行；身份检查与用户、
  凭据和 Session 写入处于同一批次，并发分配 root 角色不能绕过。条件化 D1 变更保证并发的
  禁用、删除或移除角色请求不能消灭最后一个启用的 `root`。
- 自定义角色只能在没有成员时删除。成员检查在 `DELETE` 语句内部执行，并发新增的绑定不会被
  级联删除；审计记录与删除在同一批次提交，否则一起失败。
- `roles:update` 与 `users:update` 等同于管理员权限：持有者可以扩大自己所属自定义角色的
  权限并分配任意非 root 角色，应视为完整管理授权而非受限操作权限。`settings:read` 只能
  看到运行时密钥是否已配置。
- 用户与自定义角色的创建、修改、启停、删除、密码变更标记和角色绑定，都在与变更相同的批次
  中记录操作者、Request ID、来源 IP、目标与脱敏摘要，绝不记录密码或 Hash。
- TOTP 为可选功能。启用必须等到首次正确验证码之后，废弃的二维码设置不会把用户锁在外面；
  恢复码一次性使用，关闭 TOTP 需要当前密码，可信设备 Cookie 带签名且最长 30 天，连续失败
  触发 15 分钟账户锁定。
- 密码找回使用 Better Auth 的 15 分钟一次性邮件链接；已存在与未知邮箱得到相同响应，重置后
  撤销全部现有 Session，并审计成功重置而不保存 Token 或密码。

## 密钥与敏感配置

- API 凭证 Secret、支付供应商凭证、Telegram Bot Token 和邮件通道凭据在存储前以 AES-GCM
  加密，列表接口永不返回；API Secret 只在创建或轮换时显示一次。支付连接 API Key 保存在
  独立的加密表 `payment_ingress_credentials` 中，旧明文值在首次使用时迁移并清空。设置列表
  对 `runtime.*` 密钥只返回“已配置”标记，邮件通道列表只返回是否已存储凭据；空提交保留
  现有值，因此密钥值只写不读。
- 运行时签名值在安装时由 CSPRNG 生成，并在后台维护。API 凭证 pepper 与集成密钥在仍存在
  用其加密的密文（API 凭证、连接凭据、收款方式配置、Telegram Bot 或邮件通道）时不能更换：
  请求以 `runtime_secret_in_use` 失败，必须先删除这些记录，系统没有重加密任务。Better Auth
  密钥没有对应密文，可随时轮换；更换它会使现有认证材料失效，请随数据库一起备份。
- 主密钥与其保护的密文位于同一数据库。静态加密因此只防御局部泄露（导出的单张表、日志行、
  截图），不防御整库副本。Bun 备份以明文包含这些密钥，请按
  [Bun 数据运维](./NODE_DATA_OPERATIONS.md) 把备份视为完整凭据材料。
- API 凭证使用数字 PID。轮换原地更新同一行并保留 PID，审计记录操作者/请求/IP 但不含
  Secret；之后所有 GMPay/EPay 投递（包括已按标识入队的重试）都从 D1 解析新 Secret。不保留
  已退役的凭证行；GMPay/EPay 回调按订单身份解析当前 Secret，不存在第二份回调密钥存储。
- 带凭据的交易所与钱包请求固定访问内置官方 Origin；可配置链节点只接受不含用户信息的公共
  HTTPS/WSS，并拒绝私网、保留地址和链路本地地址。
- 审计元数据写入时递归脱敏，查询和导出时再次清洗；畸形载荷不会原样回显。
- 任何收款方式和模拟器都不需要私钥或助记词，交易所凭证必须只读且无提现权限。真实供应商
  凭据不得进入源码仓库；`.dev.vars` 与 `.env` 文件已被 Git 忽略。

## 商户 API 与金额

- 金额在边界使用十进制字符串，进入计算前转换为法币最小单位整数或资产单位 `bigint`，禁止
  浮点运算。
- GMPay 必须通过启用的 PID 凭证、排序参数 HMAC-SHA256 签名、精确 Scope 与限流检查；EPay
  兼容边界保留旧版 MD5 签名。D1 是唯一的限流窗口计数器，任何最终一致缓存都不参与限流决策。
- 商户认证先验证签名与所需 Scope，再增加该凭证的 D1 限流窗口，因此无效签名不消耗成功额度。
  认证失败按提交的 PID 在独立 D1 桶中计数：一分钟内失败 20 次后端点返回 `429` 直到窗口结束，
  每次失败以 `merchant_auth_failed` 记录结构化日志，只包含 PID 与 Request ID。
- API 凭证使用显式 Scope：`orders:create`、`orders:read`、`orders:update`、`assets:read`。
  未知或聚合 Scope 会被拒绝；吊销是单向、先写者胜的转换，与审计在同一批次提交。
- 请求校验只在边界执行一次并映射为稳定错误码：`currency` 必须是有效的 ISO 4217 法币代码，
  `amount` 是最多 18 位整数、8 位小数的正十进制数，`notify_url` 必须是公网 HTTPS 端点，
  `redirect_url` 必须是 HTTPS，`token` 与 `network` 必须同时出现。超过 64 KiB 的请求体返回
  `413`。校验失败一律是 400 类响应，不会变成 `500`。
- D1 唯一约束保护凭证 PID、同一 API 凭证范围内的外部订单号、无凭证内部订单号、用户角色
  绑定、交易事件、Webhook 事件和投递。外部订单号按创建凭证隔离，既阻止同一凭证重放，也允许
  不同凭证使用各自的业务编号。
- 托管服务商（OKPay）未能创建支付时，本次支付选择与同一请求创建的商户订单一起回滚，商户
  订单号可以重试；商户收到 `provider_unavailable`（`10003`）。

## Webhook、URL 与 Queue

- 商户 `notify_url` 必须是公网 HTTPS，在随订单快照保存前拒绝本地/私网字面量和内嵌凭据。
  黑名单覆盖带尾点的主机名、IPv4 映射与兼容 IPv6、6to4、NAT64 和 Teredo 网段。投递时重新
  校验解析出的 A/AAAA 地址，私有/保留或公私混合结果失败关闭；不跟随重定向，响应最多读取
  512 字节，且不记录签名材料。Bun 上的 DNS 预检使用 DNS-over-HTTPS，而 `fetch` 会再次经系统
  解析器解析，留下很窄的重绑定窗口；若此残余风险重要，请在网络层阻断私网出网。
- 每个入站供应商端点在读取请求体、解密凭证或写入接收记录之前，先按“端点 + 客户端地址”
  申领每分钟 600 次的 D1 固定窗口配额；超限请求返回 `429` 且不写接收记录。未认证拒绝只记录
  每个客户端窗口内的前 20 次。请求体按流式字节上限读取，每次尝试分配新的服务端 Receipt ID，
  供应商提供的 `X-Request-ID` 只有通过校验后才作为可重复元数据保存。OKPay 端点对未知订单的
  应答与签名错误完全一致。
- Telegram Webhook 使用自己的限额（每个 Bot 每分钟 600 次更新、每个客户端地址每分钟 1 800
  次请求、请求体 256 KiB），并对 Telegram API 的永久性 `4xx` 拒绝返回 `200`，避免被拉黑的
  聊天阻塞投递；参见 [Telegram](./TELEGRAM.md#webhook-处理策略)。
- Queue/DLQ 消息使用显式白名单的 `kind`/`version` 信封，只携带投递/事件标识。消费者在分发前
  校验完整信封；未知、畸形或不支持版本的消息在不含正文和凭据的情况下审计，并且只有审计成功
  后才 Ack，毒消息既不会循环也不会消失。
- D1 尝试计数是权威值，每次应用层失败都会调度一条新的延迟 Queue 消息，因此可配置的应用
  最大尝试次数与单条 Cloudflare 消息的重试上限无关。Cron 驱动的 Outbox 恢复会重新入队待投递
  的首次投递、到期的失败投递，以及租约过期后停留在 `delivering` 的投递。手动重试延续尝试
  编号；当尝试已计划或已租约时返回 `409`（`webhook_delivery_retry_in_progress`）。
- 每个订单保存不可变的通知目标和创建凭证身份；手动重发会创建新的事件/投递历史行，不存在
  可变全局目标，也不会跨订单广播。回调格式没有带签名的时间戳或 nonce（协议兼容性约束），
  接收端必须按订单身份与状态去重。
- 所有 JSON API 成功与错误响应均设置 `Cache-Control: no-store` 并携带 `X-Request-ID`，避免
  订单、凭证状态、校验或基础设施响应被浏览器或中间缓存保留。

## 支付与收银台

- 支付入账、订单状态转换、Webhook 事件和投递 Outbox 一起提交并保持幂等。已确认付款的
  确认数继续增长属于重复观测：只刷新已保存的确认数，不再发出订单事件，也不改写 `paid_at`。
- 迟到付款遵循配置的 `accept`、`review` 或 `reject` 策略。待审核付款以 `pending_review`
  保存，在授权管理员明确接受前不计入订单余额，每个决定都有审计。付款已覆盖全额的订单
  （`confirming`）不会过期，已归属付款的确认数更新不经过迟到付款策略。
- 付款审核批准、支付入账、批准审计和通知 Outbox 一起提交。并发拒绝会回滚审批产生的支付
  写入；验证或持久化失败时审核保持待处理，可安全重试。
- 管理员取消/退款将订单、审计和持久化 Outbox 原子提交；Queue 派发在提交之后，可由 Outbox
  恢复。取消可恢复且幂等：受守卫的状态转换、收款目标释放和带归属的审计记录在一个 D1 批次
  中提交，乐观更新失败时三者都不写入；重试已取消订单只补写缺失的 Webhook 事件，不产生第二次
  转换或审计。
- 支付扫描使用订单快照中的资产和目标，缓存键包含收款方式、资产和目标；连接故障切换不会
  切换资产。只有网络、认证、限流和无效响应故障会改变连接健康状态。TRC20 只接受资产上预置
  的代币合约，TON 执行结果读取 toncenter 自身字段，每次历史遍历都以订单创建时间为下界，无法
  归属到共用地址订单的转账写入审计 `payment.scan_unattributed` 而不是被丢弃。
- 适配器响应在有界超时内读取，解析前限制 8 MiB 正文，供应商载荷在边界用类型化 schema
  校验。Binance/OKX 公共汇率轮询不需要私有凭据；超过 `expires_at` 的陈旧观测不会用于新订单。
- 订单只有在待支付、未过期、没有已归属付款或待审核付款人复核、且没有活跃托管订单时才能
  切换资产/网络。D1 更新受订单版本和目标地址可用性守卫；地址预留、旧地址释放和审计记录都
  绑定到成功的新版本，因此并发订单不能获得同一最终地址；版本冲突以 `order_conflict` 报告，
  不会被当作金额碰撞重试。
- 付款人提交交易标识（“已付款但未确认”）按订单和客户端地址在 D1 中限制为每分钟 5 次。
  服务端用配置的适配器拉取交易，核对订单的目标、网络和资产后，才进入正常幂等入账路径。
- 付款复核上传要求完全同源的 `Origin` 头，并按订单和客户端地址在 D1 中限制为每小时 3 次。
  服务端忽略浏览器 MIME 声明，按有界字节识别 JPEG/PNG/WebP，校验基本图像结构与尺寸，拒绝
  超过 5 MiB 的文件，并记录 SHA-256 摘要。
- 复核证据使用私有 R2 对象键。只有具备 `payment_reviews:read` 的启用用户能访问证据路由；
  未登录与无权限请求分别得到 `401`/`403`，成功响应携带 `private, no-store`、`nosniff` 与
  沙箱 CSP。批准前必须由配置的支付适配器拉取并匹配真实交易，截图不能直接改写订单状态。
- 复核描述和证据可能包含个人信息。请限制 `payment_reviews:read`，制定部署专属的 R2 生命
  周期保留策略，并在下线实例时删除保留对象。

## Telegram

- Telegram Bot Token 可在不删除订阅的情况下轮换。新 Token 先经 `getMe` 验证；启用的 Bot 在
  D1 原子更新前先用新凭据注册现有 secret-token Webhook，之后再移除旧凭据的 Webhook。若
  Telegram 无法清理旧 Webhook，后台会提示部分清理，运营者须在 BotFather 撤销旧 Token。Token
  永不由列表接口返回，也不写入审计元数据。
- 创建启用状态的 Bot 时，先验证 `getMe` 并注册 secret-token Webhook，再原子提交 Bot 与审计
  记录。Telegram 拒绝不会留下隐藏的 D1 记录；注册后 D1 提交失败时，系统会补偿删除新建的
  外部 Webhook。启用/停用请求幂等，Webhook 变更后提交失败会恢复之前的外部状态。
- `/start` 为数值发送者 ID 创建停用的私聊订阅。Telegram 查单、Inline 报价、Inline 下单、
  回调和“我已付款”检查都按所选 Bot 下已启用的私聊订阅授权发送者；群组或频道 Chat ID 不
  授予私人订单权限，未绑定用户只会看到一条“未绑定”Inline 结果。付款检查回调在入队扫描前
  以 Telegram update ID 作为 D1 幂等键，重试不会放大队列工作。该按钮只是扫描请求，不会把
  订单标记为已支付。
- 仅金额的 Inline 查询只展示启用、就绪且有可用当前报价的收款方式。所选方式编码在被选结果
  中，由正常订单服务再次校验，并且直到 Telegram 发送 `chosen_inline_result` 才加锁；伪造或
  过期的选项 ID 失败关闭。
- 通知在订单事件提交后、请求路径之外发送，遵守 Telegram 流控，并自动停用拉黑了 Bot 的私聊
  订阅。Telegram API 结果只以稳定错误码呈现给管理员。在单租户部署中，启用私聊订阅是运营者
  的信任决策：该用户可以查询实例内任意订单。

## 运行时、网络与响应

- 启用 D1 读复制后，管理列表、仪表盘、运营视图与结账读取在按请求创建的 D1 会话上执行，该会话可能由副本
  提供服务；授权、会话与设置读取、限流申领以及所有写入仍走主库。产生变更的服务端函数与结账 API 响应会设置
  `gmpay_d1_bookmark` cookie（HttpOnly，五分钟，不含个人数据），使同一浏览器随后的读取锚定在该次写入之后；
  伪造的 cookie 值会被忽略。管理端请求一到达就启动 Better Auth 会话查询，与 Allowed Hosts 设置读取并行；
  一旦发现运行时密钥或可信来源已变更，该乐观结果即被丢弃并重新查询。
- 响应在 HTTPS 上启用 HSTS，并设置禁止 Frame、MIME Sniffing 防护、严格 Referrer Policy、
  受限 Permissions Policy、同源资源策略和内容安全策略（CSP）。生产环境必须配置 Allowed
  Hosts、Origin/CSRF 校验以及登录和 API 限流。
- Cloudflare Workers 上的客户端地址是平台设置的 `cf-connecting-ip`。Bun 上唯一可信的事实是
  TCP 对端：只有对端是回环、私有或链路本地地址时才采纳转发头，`X-Forwarded-For` 最右侧一跳
  成为客户端地址，`X-Forwarded-Proto: https` 把请求标记为 HTTPS（启用 HSTS 与安全 Cookie），
  入站的 `cf-connecting-ip` 始终被覆盖。公网对端本身即客户端，其转发头一律丢弃，因此按地址
  的限流和审计记录无法伪造。代理契约见[部署指南](./DEPLOYMENT.md#反向代理与-tls)。
- SMTP 通道拒绝 25 端口和非公网主机，始终校验 TLS 证书，在 465 端口使用隐式 TLS；其他端口
  先探测 `EHLO`，服务器未宣告 `STARTTLS` 时拒绝投递，凭据与邮件内容不会以明文传输。测试
  邮件需要 `settings:update` 权限，会被审计，且每个用户每小时最多 5 次。
- 公共 `/status` 与 `/assets` 加载器提供 10 秒的实例内快照，匿名突发流量共享一次查询。
- 两类第三方资源从 `cdn.jsdmirror.com` 加载：`/docs` 的 Scalar API 文档（固定版本、`sha384`
  Subresource Integrity 和仅该路由生效的 CSP `script-src` 白名单）以及加密货币图标集（图片，
  带 jsDelivr 与 GitHub 回退）。这是一个供应链信任点；无法接受的部署应从自有源自托管这两类
  资源，并把该 CDN 从 CSP 中移除。
- Bun 持久队列与 Cloudflare 的投递预算一致（一次投递加配置的重试次数），为最慢的处理器保留
  足够长的租约，并在空闲轮询中清理七天前的死信行。

## 运维、审计与迁移

- 手动运维任务需要独立于只读健康面板的 `operations:update` 权限。运营者每次请求只运行一个
  有界任务：订单过期、Webhook Outbox 恢复、RPC 健康刷新或汇率同步。成功结果归属到操作者/
  请求/IP；失败只保存稳定错误码，绝不保存供应商响应或异常文本。
- 写入审计记录并在 `X-Request-ID` 中回显的 Request ID 必须匹配 `^[A-Za-z0-9._:-]{1,128}$`；
  缺失或不合法的客户端值会被服务端生成的 UUID 替换。
- 保留清理在每逢第五分钟的维护 tick 上以有界分块运行（每条语句 250 行，每次最多 2,000 行或两秒），
  只要还有过期行就在下一个保留分钟继续，因此持续产生的投递、接收记录和任务运行记录不会超出清理能力，
  删除操作也不会每分钟都与用户请求争抢 D1 写入者。
- Provider-event 迁移 `0007_sparkling_wallflower.sql` 新增可空租约令牌，不重写已有行。单次
  租约为五分钟（最多八次各 30 秒的 EVM 查询加余量）。入账、完成、失败和来源健康更新均检查
  令牌与到期时间；恢复操作使旧持有者失效，旧的处理中记录在原租约到期后仍可恢复。
- 迁移 `0009_audit_hardening.sql` 把 Outbox 部分索引扩展到 `delivering` 投递，为投递、事件和
  收款方式锁新增按订单的索引，把旧 `detected` 状态下等待审核的迟到付款迁移为 `pending_review`，
  并删除未使用的 `runtime.retention_schedule` 设置。Worker 部署前先运行正常 D1 迁移；Bun 在
  启动时迁移。
