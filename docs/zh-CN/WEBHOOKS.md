# Webhook

简体中文 · [English](../en-US/WEBHOOKS.md)

GMPay Edge 将系统入站端点与订单级出站通知明确分开。

## 入站端点

入站端点是安装时初始化的“仅路径”目录，用于供应商回调和 Telegram。数据库不保存部署域名；后台详情页使用当前 Origin 生成示例 URL，并展示已脱敏的接收记录、签名结果、处理状态、耗时和安全错误码。

部署主机统一在“安全设置 → Allowed Hosts”配置，由全局中间件同时约束普通请求和回调。

每个供应商端点在读取请求体、解密凭证或写入接收记录之前，都会先在权威数据库中按“端点 + 客户端地址”申领固定窗口配额（每分钟 600 次）；超出配额的请求直接返回 `429`，不写接收记录。已通过认证的结果与服务端失败始终记录；签名验证前的未认证拒绝（`4xx`）只记录每个客户端窗口内的前 20 次，避免垃圾流量填满接收记录表。接收记录的外部请求 ID 即响应头 `x-request-id` 中回显的、经过校验的标识。OKPay 端点对未知订单的应答与签名错误完全一致。Telegram Webhook 使用自己的按 Bot 与按客户端地址配额及应答策略，参见 [Telegram](TELEGRAM.md#webhook-处理策略)。

## 订单通知地址

商户创建订单时可以传入 `notify_url`。系统只接受公共 HTTPS URL，并把它与创建订单的 API 凭证身份一起不可变地保存到订单。系统没有全局回调目标，也不会把某订单事件广播到其他订单地址。私网、回环、链路本地、云元数据、带凭证或依赖不安全跳转的目标都会被拒绝。

## 签名校验

GMPay JSON 回调包含 `signature`，算法为：排除签名字段和空值，将回调字段按 ASCII 名称升序拼接，并以 API Secret 为 Key 计算小写 HMAC-SHA256。EPay 回调使用带 `sign` 与 `sign_type=MD5` 的 GET Query。轮换 Secret 不改变 PID 和订单引用；后续投递及手动重发都会使用新 Secret。

请使用常量时间比较签名，并按交易或订单身份进行幂等去重。[商户 API 文档](MERCHANT_API.md#gmpay-通知)提供可运行的 Bun 验签示例；生产接收端应先持久化事件身份，再返回纯文本 `ok`。

GMPay 与 EPay 回调格式受协议兼容性约束：签名只覆盖业务字段，没有带签名的时间戳或 nonce；事件 ID 与投递 ID 只出现在未签名的 `x-gmpay-event-id`、`x-gmpay-delivery-id` 请求头中。因此被截获的回调在 TLS 传输之外可能被重放，接收端必须把投递视为“至少一次”，并按自己已持久化的交易/订单身份与状态去重，而不能依赖消息的新鲜度。

## 投递语义

- 只有 HTTP `200` 且响应正文为纯文本 `ok` 才视为成功。
- 投递状态和每次尝试都保存在 D1。
- Queue 消息只携带标识符，不携带 Secret。
- 失败使用有界指数退避，并遵守后台配置的最大尝试次数。
- Outbox 恢复会幂等重入队遗漏的首次投递与到期重试，也包括停留在 `delivering`、消费者租约已过期却没有记录结果的投递；该投递以下一个尝试序号继续。
- 商户请求发出之前的基础设施故障（数据库读取、DNS 预检）会归还占用并让 Queue 重投同一尝试，既不消耗尝试次数，也不写入尝试记录。
- 手动重试复用相同事件载荷并延续尝试编号（第 N+1 次），不会覆盖历史尝试记录。`dead` 投递可随时手动重试；`failed` 或租约过期的 `delivering` 投递只有在没有已计划或已租约的尝试时才接受重试，否则返回“重试正在进行”。手动尝试失败且达到最大尝试次数时，投递再次进入 `dead`，可以再次重试。
- 管理员可重发订单当前状态；系统新增一条手动事件和投递记录，不覆盖历史成功记录。
- 响应摘要和审计数据有大小上限并进行敏感字段脱敏；纯文本响应摘要会保留（最多 512 字节），其中明显的 `key=value` 密钥会被掩码。

“出站通知”表格提供投递详情弹窗，集中展示事件载荷和按最新优先排列的完整尝试记录。每次尝试会保存实际使用的请求方法、目标、请求头、请求体或查询参数，但签名值统一保存为 `[REDACTED]`，解密凭证绝不持久化。缺失或非法快照会显示为不可用，不根据当前订单状态重建。

支付入账、订单状态转换、Webhook 事件和投递 Outbox 必须在同一事务中提交。重复链上或供应商事件不能生成重复业务事件或回调。

已终结的投递历史遵循审计保留期设置。保留清理在每次维护 tick 上以有界分块运行，只要还有过期行就会在下一 tick 继续，因此持续产生的投递、接收记录和任务运行记录不会超出清理能力。

## 运行时说明

- Workers 出网无法到达私有网络。Bun 上的 DNS 预检会在请求前通过 DNS-over-HTTPS 解析回调主机，但 `fetch` 会再次使用系统解析器解析域名，因此重绑定 DNS 服务器仍有一个很窄的窗口。若此残余风险重要，请让 Bun 部署运行在阻止私有网段的出网策略之后。
- Bun 持久队列与 Cloudflare 的投递预算一致（一次投递加配置的重试次数），并为最慢的处理器保留足够长的租约。死信行会在“队列监控”页面计数，并在空闲轮询中于七天后清理。

## 生产验证

1. 使用能记录原始 Body 与 Header 的 HTTPS 接收端。
2. 验证正确签名可通过，篡改回调参数会被拒绝。
3. 分别返回 `500`、超时和重定向，验证重试与 SSRF 防护。
4. 重放相同事件 ID，验证应用级去重。
5. 停止并恢复 Queue 消费者，确认 Outbox 能继续投递。
